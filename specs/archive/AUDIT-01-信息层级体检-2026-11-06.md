## 0. 一页结论

MD Viewer 的阅读面很克制，问题不在“内容区太吵”，而在**壳里有一批已经做好、却没接到默认外壳上的入口**。默认外壳是自定义菜单，最近文件却只挂在永远不会出现的原生菜单上；单文件时标签条被隐藏，关闭文件的入口也随之消失；菜单项、标签、目录又都只有鼠标路径。与此同时，视图菜单把四组控制压成八项，状态栏则被自动保存提示当成了通知栏。

- 默认 `window.chrome=custom`；自定义 File 菜单只有 6 个叶子项，没有「最近文件」。`recent_files` 仍维护 10 条，`refresh_recent_menu` 刷新的是一个没挂到窗口上的 Tk 菜单。
- `tabbar.hidden = list.length < 2`；File 菜单没有「关闭」，全局键没有 Ctrl+W。单文件时，关闭文件只剩“退出应用”。
- 菜单项是 `div`、标签是 `div`、TOC 项是 `div`，只挂了 click。6 个顶级菜单按钮能 Tab 到，但菜单里面进不去；关闭标签也没有键盘路径。
- 首屏 7 条快捷键、帮助 8 条、代码 10 个全局分支；三份都不含 Ctrl+K / Ctrl+Shift+O / Ctrl+Shift+P，命令面板没有菜单入口。
- 状态栏右侧最多 5 段（行列 / 卷章 / 编码 / 文件名 / 主题）；自动保存每 2 秒用「已自动保存」替换整段，下一次统计刷新又会立刻把提示覆盖。

**如果只做一件事**：IA-03，给菜单项、标签、TOC 补键盘语义，并加 Ctrl+W。它是唯一“没有鼠标就完不成”的硬阻断，且是 A 级纯实现，不动视觉。

## 1. 判定口径

| 原则 | 在本项目里的含义 | 不达标时用户会怎样 |
|---|---|---|
| **单一入口** | 同一个功能只应有一个主要入口；菜单、快捷键、命令面板可以并存，但不能互相矛盾 | 不知道以哪个为准；设置看起来“没生效” |
| **主路径可达** | 打开、切换、关闭、保存四个动作，鼠标和键盘都能走完 | 少一个入口就卡在动作中间，只能退出重来 |
| **状态可见** | 当前模式、当前文件、当前目录状态要在一眼之内 | 不知道自己在读还是在写；不知道目录为什么出现/消失 |
| **渐进披露** | 首次只给下一步；字体、主题、目录规则等低频项收进分组 | 首屏被低频选项占满，真正要点的东西找不到 |
| **静默反馈** | 自动保存等后台动作不抢状态栏，失败才出声 | 写作时状态栏反复闪，注意力被拉回界面 |
| **一处真源** | 快捷键、菜单、文案、配置只有一个来源 | 同一件事有三种说法，新增一项必漏一处 |
| **空态有出口** | 没有内容时告诉用户下一步，而不是留一块空白 | 打开先看到“未命名”或“无目录”，不知道从哪开始 |

## 2. P1 · 高影响

### IA-01 默认外壳里「最近文件」没有任何入口

**现象**：默认配置 `window.chrome=custom`。自定义菜单模型 `buildMenuModel` 的「文件」只有打开、新建、保存、另存为、导出 HTML、退出 6 项，没有「最近文件」。但 `actions.py` 仍在每次切标签时把 `recent_files` 维护到 10 条，`main_window.py` 也仍在刷新 `recent_menu`——这个 Tk 菜单只在 `chrome=native` 时才挂到窗口上。当前配置文件里实际存了 10 条最近路径，界面里 0 条可见。

**证据**：`app.js::buildMenuModel`（文件分组）；`main_window.py::_build_menu`（`recent_menu` 与 `if self._chrome == "native"`）；`actions.py::_save_recent`；`core/config.py::DEFAULTS`（`recent_files`）；`.md-viewer-config.json::recent_files`

**原则**：单一入口 / 主路径可达

**影响**：用户想接着看昨天那份文档，只能按 Ctrl+O 重新浏览文件夹。最近文件是 README 明确宣传的能力（“会话恢复 + 最近文件”），现在变成“后台在记、前台看不见”。这不是少一个快捷方式，而是一个已交付功能在默认外壳里完全不可达。

**改法**：
1. 在 `_send_ui_meta` 里下发 `recent`（最多 10 条），`buildMenuModel` 的「文件」增加「最近文件」子菜单，末尾放「清除列表」。
2. 若确定只保留原生外壳，则从 README 删掉「最近文件」，并停止刷新隐藏菜单；不推荐，因为数据层已经完整。
3. 原生回退与自定义菜单要么共用一份模型，要么在规格里明确“原生仅为调试回退”。

**规格影响**：**需确认**（新增一个菜单入口；不动视觉口径）

**验收问题**：默认自定义外壳下，文件菜单能否直接看到 10 条最近文件，并一键打开？

### IA-02 单文件时标签条、关闭入口、关闭快捷键同时消失

**现象**：`setTabs` 在 `list.length < 2` 时把标签条整个隐藏。自定义 File 菜单没有「关闭」；全局快捷键没有 Ctrl+W；唯一的关闭按钮 `.tab .close` 只在标签上，且默认 `visibility: hidden`，悬停或激活才出现。关闭最后一个标签时，`_do_close` 会新建一个「未命名」标签并重新灌入欢迎文本，所以标签条永远不会以“1 个标签”的形态出现。

**证据**：`app.js::MDV.setTabs`（`tabbar.hidden = list.length < 2`）；`app.js::buildMenuModel`（File 6 项）；`app.js` 全局 keydown（无 `w` 分支）；`actions.py::_do_close`（无标签时重建欢迎页）；`app.css::.tab .close`

**原则**：主路径可达

**影响**：只开一个文件时，用户无法“关掉这个文件、让应用留着”。要换文件只能再打开一个（此时才出现标签条），要清空只能退出应用。多标签是产品宣传的能力，但第一次使用时完全看不见，用户会把它当成单文档阅读器。

**改法**：
1. File 菜单加「关闭文件」，绑定 Ctrl+W，走现有 `closeTab` 事件。
2. 只有 1 个文档时也显示标签条；可用 28px 的单标签形态，保留“内容优先”的意图，但不要隐藏到 0。
3. 关闭最后一个文档后进入空态/欢迎页，而不是悄悄新建一个「未命名」。

**规格影响**：**需确认**（改外壳行为；菜单项与快捷键本身是 A 级）

**验收问题**：只开一个文件，用鼠标和键盘各关一次，应用是否仍然开着？

### IA-03 菜单项、标签、目录都是 div，键盘只能停在菜单标题

**现象**：6 个顶级菜单按钮是 `<button>`，但 38 个菜单行是 `<div class="menu-item">`；标签是 `<div class="tab">`，关闭是 `<span class="close">`；TOC 项是 `<div class="toc-item">`。三者都只挂 click，没有 `tabindex`、`role`，没有 ArrowUp/Down、Home/End、Enter/Space、Escape 处理。全局 keydown 也没有 Ctrl+W。

**证据**：`app.js::renderMenus`（`menuEl("div", "menu-item")` 与行 click）；`app.js::MDV.setTabs`（`div.tab` / `span.close`）；`toc.js::nodeRow`（`div.toc-item`）；`toc.js::initToc`（只挂 click 委托）；`app.js` 全局 keydown

**原则**：可键盘完成

**影响**：键盘用户能 Tab 到菜单标题，按 Enter 也能打开，但焦点进不去菜单项，所以选不了主题、字体、阅读模式、目录模式；能 Tab 到标签标题（如果标签条存在），但关不掉；TOC 只能鼠标点。全局快捷键还能完成打开/保存/退出，但“关闭标签、换主题、换字体、跳章”这几件事没有鼠标就做不了。这是硬阻断，不是效率问题。

**改法**：
1. 菜单：行改为 `button role="menuitem"`，或 `tabindex="-1"` + roving focus；ArrowUp/Down 移动，Home/End 到首尾，Enter/Space 执行，Escape 关闭并把焦点还给触发按钮。
2. 标签：`role="tab"`、`aria-selected`；Enter/Space 激活，Delete 或 Ctrl+W 关闭；关闭按钮改成 `<button aria-label="关闭 文件名">`。
3. TOC：`role="treeitem"` 或 `<button>`；Enter 跳转，当前项 `aria-current="true"`；保留现有 Ctrl+←/→ 作为章间跳转。
4. 全局加 Ctrl+W，并在 File 菜单加「关闭文件」。

**规格影响**：无（纯实现，不改视觉）

**验收问题**：拔掉鼠标，能否完成“打开 → 切标签 → 关标签 → 换主题 → 开关目录 → 跳章”？

### IA-04 首屏、帮助、代码三份快捷键表互不一致，Ctrl+K 无处可学

**现象**：`welcome.py` 的首屏表 7 行；`main_window.py::_show_help` 的对话框 8 行；代码里的全局 keydown 有 10 个分支（12 个组合键），编辑器另有 CodeMirror keymap。三份都不含 Ctrl+K（命令面板）、Ctrl+Shift+O（目录）、Ctrl+Shift+P（导出 HTML）、Ctrl+←/→（章间跳转）；帮助比首屏多 Ctrl+Shift+S，首屏完全没有；Ctrl+H 在帮助和菜单里都宣传，但全局 keydown 只处理了 `f`，`h` 只在编辑器 keymap 里生效，所以阅读态按 Ctrl+H 没反应。

**证据**：`welcome.py::WELCOME`；`main_window.py::_show_help`；`app.js` 全局 keydown；`editor.js::buildExtensions`（`Mod-h`）

**原则**：一处真源

**影响**：用户永远学不到命令面板和目录快捷键；Ctrl+H 在阅读态看起来是坏的；每新增一个快捷键，三份表就再漂一次。命令面板是完整的第二套命令入口，却只写在它自己的输入框 placeholder 里——不打开就看不到，形成循环依赖。

**改法**：
1. 建一份 `SHORTCUTS` 表（id、组合键、说明、作用域），首屏、帮助、命令面板都从它渲染。
2. 在「视图」或「帮助」加「命令面板 Ctrl+K」；帮助补 Ctrl+Shift+O、Ctrl+Shift+P、Ctrl+←/→。
3. 全局 keydown 补 `h` 分支，调用 `MDV.runCmd("find")`，让阅读态也能打开查找/替换。

**规格影响**：**需确认**（文案与菜单入口；`h` 分支是 A 级）

**验收问题**：代码里出现的每个组合键，是否都能在帮助里找到一次，且它在声称的作用域里真的有效？

## 3. P2 · 中等影响

### IA-05 「显示目录」和「目录显示模式」会同时显示互相矛盾的状态

**现象**：视图菜单里有两个目录控制：复选「显示目录」+ 三态「目录：自动 / 始终显示 / 始终隐藏」。手动切换走 `MDV.toggleToc` → `setTocVisible`，只写 `manual`，不改 `uiMeta.tocMode`。因此当 `toc_mode=never` 时点「显示目录」，目录会出现，但菜单里「目录：始终隐藏」仍然是勾选状态；反过来，`toc_visible=false` 与 `toc_mode=auto` 并存时，书卷模式也不会显示目录，但菜单仍写着“自动（书卷显示 / 文档隐藏）”。

**证据**：`app.js::buildMenuModel`（`check: "toc"` 与 `radio: "tocmode"` 两组）；`app.js::MDV.toggleToc`；`toc.js::shouldShow`；`toc.js::setTocVisible`；`specs/06-配置与持久化.md::R-06-07`

**原则**：状态可见 / 单一入口

**影响**：用户无法从菜单判断“现在到底按哪条规则”。隐藏目录后切到书卷，它又出现；选了“始终隐藏”，点一下「显示目录」又能出现，且两个勾同时亮。用户会认为设置没有保存，或者菜单坏了。代码里的优先级（手动 > toc_mode > auto）其实是对的，问题在 UI 没有把“当前依据”说出来。

**改法**：
1. 保留一个主动作 + 一个默认规则：主动作「切换目录」不显示勾选态，默认规则才用三态；或反过来，复选保留，三态收进「默认规则」子菜单。
2. 菜单顶部加一行只读状态：「当前：显示（手动）/ 隐藏（自动）/ 显示（始终）」。
3. 手动切换时把 `tocMode` 置回 `auto`（或同步更新三态），避免两个勾同时亮。

**规格影响**：**需确认**（改目录 UI，不改 `R-06-07` 的优先级语义）

**验收问题**：任意时刻，目录相关控件里是否最多只有一个勾选态，且菜单能说清“为什么”？

### IA-06 视图菜单把四组控制压成八项，字体和主题各占一个顶级菜单

**现象**：顶级菜单 6 个，叶子项合计 38 个：文件 6、编辑 9、视图 8、字体 9、主题 4、帮助 2。视图 8 项被 3 条分隔线切成 4 组（编辑⇄阅读 / 排版三态 / 显示目录 / 目录模式三态）；字体 9 项和主题 4 项各占一个顶级位置。外观类设置占 2/6 的顶级名额，而“目录”在视图里出现两次。

**证据**：`app.js::buildMenuModel`；`main_window.py::_build_menu`；`core/theme.py::READING_FONTS`

**原则**：渐进披露

**影响**：6 个顶级菜单本身不算多，问题是分组：视图第一层 8 行、3 条分隔线，用户要逐行读完才知道“排版”和“目录”是两件事；字体是 9 个单选项，却和“文件/编辑”同级。结果是低频的外观设置占了最显眼的位置，高频的“切模式/开目录”反而埋在 8 行里。

**改法**：
1. 顶级收成 4 个：文件 / 编辑 / 视图 / 帮助。
2. 视图下分 3 组：模式（编辑⇄阅读、排版模式）、目录（显示、规则）、外观（主题、字体）。
3. 保留全部 38 个功能，只改分组与层级；PhotoMM 对齐的是尺寸与质感，不是菜单项树。

**规格影响**：**需确认**（动外壳菜单结构）

**验收问题**：第一次打开的人，能否在 2 次点击内找到“换主题”，并在视图第一层看到不超过 5 行？

### IA-07 命令面板是第二套完整菜单，但不显示勾选态和快捷键

**现象**：`collectCommands` 把 `buildMenuModel` 的 38 个叶子项平铺成「菜单 › 项」，筛选是 `indexOf` 子串匹配。每行只有 label：没有勾选态、没有快捷键、没有分组标题。菜单里能看到的“当前主题 / 当前字体 / 当前目录模式”，在面板里全部丢失；面板也没有菜单入口，唯一提示是它自己的输入框 placeholder。

**证据**：`app.js::collectCommands`；`app.js::renderPalette`；`app.js::buildMenuModel`；`app.html::#palette-input`

**原则**：状态可见 / 渐进披露

**影响**：用户输入“主题”后看到 4 行主题名，但不知道当前是哪一套，只能先执行再回来看；输入“目录”看到 4 行，也分不清哪个是当前规则。面板本来是最快的入口，却因为缺少状态而变成“盲选”。同时它不可发现（见 IA-04），新用户根本不会打开。

**改法**：
1. 行结构改成「label + 快捷键 + 勾选标记」，按菜单加分组标题。
2. 视图/帮助菜单加「命令面板 Ctrl+K」。
3. 筛选可以保留子串（可预测），也可以升级为子序列匹配；无论哪种，在 placeholder 里写清规则。

**规格影响**：**需确认**（UI 增加，不改规则）

**验收问题**：打开面板输入“主题”，不按 Enter 能否看出当前主题是哪一套？

### IA-08 状态栏右侧五段信息互相竞争，自动保存每 2 秒把它变成通知栏

**现象**：右侧最多拼 5 段：`行:列 | 卷·章·百分比 | 编码 | 文件名 | 主题名`。临时消息 `set_temp` 默认 2000ms，直接把整段替换掉；自动保存在 docChanged 后 2 秒触发，成功时调用 `set_temp("已自动保存")`。另外，`MDV.setStatus` 写右槽时无条件覆盖，所以临时消息期间任何一次统计/信息刷新都会立刻把提示顶掉。

**证据**：`main.pyw::_update_status_tail`；`main.pyw::_auto_save`；`statusbar.py::set_temp`；`app.js::MDV.setStatus` / `MDV.setStatusTemp`

**原则**：静默反馈 / 状态可见

**影响**：写作时每停 2 秒，行列和章节就被“已自动保存”替换 2 秒；如果期间还有统计刷新，提示可能一闪而过。用户想瞄一眼“我在第几章”时，经常正好被通知占着。文件名已经在标题栏和标签上出现，状态栏再写一遍是纯重复。规格里写的是“静默自动保存”，现在的实现不是静默，是每 2 秒报一次平安。

**改法**：
1. 固定槽位：左＝字数/词数；中＝行列 + 卷章/百分比；右＝编码 + 主题。删掉文件名。
2. 自动保存成功不显示文字；最多用一个 6px 的小点，失败才 `set_temp`。
3. 临时消息走独立的一行/浮层，或状态栏里保留一个专用槽，不覆盖基础信息。
4. `setStatus` 在 `_statusTimer` 活动期间不写右槽；`set_temp` 结束后再恢复。

**规格影响**：**需确认**（状态栏层级；去掉自动保存提示是 A 级）

**验收问题**：连续写作 10 秒，行列和章节是否始终可见，且保存确认不会把它们擦掉？

### IA-09 阅读/编辑没有常驻指示，F2 只存在于菜单和欢迎页

**现象**：`setMode` 只切换 `hidden`，状态栏没有 mode 字段，标题栏只有文件名/脏标记。F2 出现在视图菜单一项、欢迎页一行、帮助对话框一行；工作面本身没有任何“现在是阅读还是编辑”的标签，也没有“F2 可切换”的提示。

**证据**：`app.js::setMode`；`main.pyw::_update_status_tail`；`app.js::buildMenuModel`；`welcome.py::WELCOME`

**原则**：状态可见

**影响**：第一次打开 Markdown 的人看到的是排版后的纸面，产品名又叫 MD Viewer，很容易把它当成只读阅读器；关掉欢迎页后，这个印象就没有东西纠正。反过来，在编辑态的人如果不记得 F2，也会去找菜单。核心交互只靠记忆，不靠界面。

**改法**：
1. 状态栏左侧或标题栏加一个单词 chip：「阅读」/「编辑」，悬停提示「F2 切换」。
2. 首次启动保留欢迎页提示；之后 chip 就是常驻的可发现入口。
3. 不要做成大按钮或工具栏——一个词足够，符合“界面被遗忘”。

**规格影响**：**需确认**（视觉增加一个小状态）

**验收问题**：一个从没打开过帮助的人，能否在 5 秒内找到“怎么开始编辑”？

### IA-10 欢迎页其实是一个可编辑的「未命名」文档，不是空态

**现象**：`WELCOME` 是一段 Markdown 字符串，启动无文件时通过 `new_tab` + `send_text` 灌进普通标签，标签名是「未命名」。它有正文，所以 `commitDoc` 进入阅读态；按 F2 就能编辑；没有路径，自动保存会跳过；关闭最后一个标签时 `_do_close` 又新建一个未命名标签并重新灌入同一段文本。应用没有真正的空态。

**证据**：`welcome.py::WELCOME`；`actions.py::_do_close`；`actions.py::new_tab`；`app.js::commitDoc`

**原则**：空态有出口

**影响**：用户可能把欢迎页当草稿直接输入，按 Ctrl+S 才被要求“另存为”；也可能以为这是一份示例文件，关掉后它又回来。欢迎页占一个标签位，且和真实文档长得一样，用户分不清“这是应用在说话”还是“这是我的内容”。对第一次使用的人来说，空态应该给三个动作，而不是给一篇可编辑的文章。

**改法**：
1. 做独立于文档模型的开始页：打开文件 / 新建 / 最近文件 + 快捷键摘要，不可编辑。
2. 如果保留 Markdown 欢迎页，标签名改成「欢迎（示例，只读）」，禁用 F2/保存，并且不计入标签数。
3. 关闭最后一个文档 → 开始页，而不是新的「未命名」。

**规格影响**：**需重做**（新增一种“非文档”状态）

**验收问题**：关闭最后一个文档后，看到的是不是一个不可编辑、带三个动作的开始页？

## 5. 已经做对的部分（改的时候不要一起动）

- `core/theme.py::css_vars` / `shell_vars` 是颜色唯一真源；`app.css` 只消费变量，四套主题没有散落色值。改菜单/状态栏时不要去写死颜色。
- 外壳尺寸严格落在 `specs/00` 的 44 / 36 / 24 px 与 10px 圆角上，没有额外工具栏；这是“内容优先”成立的前提。
- `toc.js::shouldShow` 的优先级（手动 > toc_mode > auto）和“手动隐藏只作用于当前排版模式”的逃生阀写得很清楚，代码也按规格落地了。IA-05 要改的是呈现，不是这套语义。
- `toc.js::windowize` 在超过 200 项时只渲染可见窗，固定 36px 行高；3955 项的书也能开目录。这是本项目最成熟的一处渐进披露。
- `reader.js::renderWindow` / `RENDER_BUDGET` 的分块渲染与占位撑高，让几十 MB 的文档也能翻到底；不要为了“统一”把阅读区改成整页渲染。
- `app.js::setMode` 在 F2 时保留编辑/阅读各自的滚动位置，并用 `anchorLineFromReader` / `anchorReaderFromEditor` 对齐光标；多标签的 `EditorState` 隔离撤销历史。改模式指示时不要碰这套锚点逻辑。
- 命令面板的键盘机制（ArrowUp/Down、Enter、Escape）已经完整；缺的是状态、快捷键列和入口，不是重写。
- `app.css::@media (prefers-reduced-motion)` 已经存在，且全项目没有无限循环/装饰性动画；动效基线是克制的（详见 AUDIT-02）。

## 6. 建议动作顺序

| 顺序 | 动作 | 审批 | 理由 |
|---|---|---|---|
| 1 | IA-03 键盘语义 + Ctrl+W | A | 唯一硬阻断；纯实现，不改视觉 |
| 2 | IA-01 最近文件接回自定义菜单 | B | 数据已存在，补一个菜单即可救活一个已交付功能 |
| 3 | IA-02 关闭文件入口 + 单标签形态 | B | 修掉“只能退出应用”的死路 |
| 4 | IA-04 快捷键一处真源 + 补 Ctrl+H | B | 成本低，直接决定命令面板能否被学会 |
| 5 | IA-08 状态栏固定槽 + 静默自动保存 | B | 高频纸割；改完写作时不再被“已自动保存”打断 |
| 6 | IA-05 目录控制去重 | B | 先解决“两个勾同时亮”的矛盾，再谈分组 |
| 7 | IA-06 菜单分组重排 | B | 影响扫描成本，但不影响完成；可与 IA-05 同批 |
| 8 | IA-07 命令面板显示勾选与快捷键 | B | 依赖 IA-04 的真源；做完面板才真正可用 |
| 9 | IA-09 模式 chip | B | 小视觉改动，补上核心交互的常驻提示 |
| 10 | IA-10 欢迎页改成开始页 | C | 新增“非文档”状态，需先出方案 |

**A 级（开发可自行判断）**：IA-03；P3-02、P3-07。
**B 级（需产品/老板点头）**：IA-01、IA-02、IA-04 至 IA-09；P3-01、P3-03 至 P3-06。
**C 级（需先出方案）**：IA-10。

**排序理由**：先做 A 级的硬阻断；再做“已有数据/已有逻辑，只差接线”的 IA-01、IA-02；然后处理学习成本（IA-04）和高频反馈（IA-08）；最后才是菜单重排、面板状态和视觉新增。IA-10 动的是文档模型之外的新状态，单独走方案。
